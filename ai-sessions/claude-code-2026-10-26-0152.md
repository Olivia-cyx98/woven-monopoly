### Claude

You don't need it. It's only a way to avoid copying the same board into several spec files, and both choices are fine.

**How it works:** `spec_helper` adds the helper's methods to every spec, so inside any spec you can write `test_board` and get the four-space board. For example, in game_spec:

```ruby
# before: 10 lines
let(:board) do
  WovenMonopoly::Board.new(
    [
      WovenMonopoly::Space.new(name: 'GO', type: 'go'),
      # ...3 more spaces
    ]
  )
end

# after: 1 line
let(:board) { test_board }
```

That's the whole benefit: the board is defined once in [test_board.rb](spec/support/test_board.rb) instead of three times, and changing it means editing one file.

**Why you might not want it:** someone reading game_spec can no longer see what's on the board without opening another file. Tests like "lands on Red 1" or "board size is 4" only make sense once you know the board's contents. In a coding test, reviewers read the specs, so having the data in the spec they're reading is a fair reason to keep the copies.

If it doesn't feel useful to you, delete it:

```sh
git checkout spec/spec_helper.rb
rm -r spec/support
```

Three copies of a four-line board is a small amount of duplication, and nobody will mark you down for it. Want me to remove it?

`spec_helper.rb` is RSpec's setup file. Because [.rspec](.rspec) says `--require spec_helper`, RSpec loads it once before running any test. Anything every spec needs goes here, so the individual spec files don't have to repeat it.

Here's what each part of [spec_helper.rb](spec/spec_helper.rb) does:

| Line | What it does |
|---|---|
| `require_relative '../lib/woven_monopoly'` | Loads your game code. Without it, no spec could find `WovenMonopoly::Board`, `Game`, and so on. |
| `Dir[...support...].each { require }` | Loads every helper file in `spec/support/` (right now just `test_board.rb`). |
| `config.include TestBoard` | Lets any spec call `test_spaces` and `test_board`. |
| `include_chain_clauses_in_custom_matcher_descriptions` | Makes failure messages more detailed for chained matchers. This is RSpec's default setting. |
| `verify_partial_doubles = true` | If a test stubs a method that doesn't exist on the real object, the test fails. That catches tests that keep passing after a method is renamed. |
| `shared_context_metadata_behavior` | Newer behaviour for shared contexts. This is RSpec's default setting, and you don't use shared contexts. |
| `disable_monkey_patching!` | Requires writing `RSpec.describe` instead of a bare `describe`, so RSpec doesn't add methods to every Ruby object. |
| `config.order = :random` + `Kernel.srand config.seed` | Runs tests in a random order each time. If one test depends on something another test left behind, it shows up as an occasional failure. The seed is printed at the end (e.g. `Randomized with seed 63108`), and `rspec --seed 63108` replays that exact order. |

Only the first three lines are specific to your project. The rest is the standard setup that `rspec --init` generates.
